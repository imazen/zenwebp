# #71 probe — where the m5 screenshot gap actually is (2026-08-28)

Issue #71 says zenwebp's greedy per-tile predictor selection at 16px tiles
(bits=4, m5/m6) produces a worse stream than libwebp's on `weather`
(990×1390) and `archives` (1280×1558), and lists three remaining suspects:
(1) mode-image entropy coding, (2) cross-color tile selection at fine
tiles, (3) greedy tie-breaking in `GetBestPredictorForTile`.

Tool: `dev/issue71_probe.rs` (`cargo run --release --features mode_debug
--example issue71_probe -- --methods 4,5 <png>...`). It encodes each PNG
losslessly with zenwebp and libwebp (webpx 0.4.0 / libwebp-sys 0.14.4,
`exact=true` both sides), then parses BOTH streams with zenwebp's decoder
(`decoder::vp8l_transform_dump`, a `mode_debug` diagnostic added for this)
and reports per transform the bits it cost on the wire, the tile grid, the
per-mode histogram, the tile-by-tile agreement of the two mode maps, and
the main image's cache bits / histo bits / group count / entropy-image,
Huffman-table and pixel-data bit costs. Host: Apple M4 Pro, aarch64.

On all four cells the predictor mode maps are **identical tile for tile**
(1364/1364, 5394/5394, 1960/1960, 7840/7840), so are the cross-color
tiles, the predictor sub-image costs exactly the same bits in both
streams, and both encoders pick the same `histo_bits` and `cache_bits`.
There is no predictor-selection or mode-image-coding gap: zenwebp's
fine-tile selection *is* libwebp's, byte for byte.

Two things differ:

* **The cross-color sub-image costs zenwebp more bits for identical data**
  (weather m5 23 264 vs 21 962; archives m5 39 555 vs 37 374 — 163 B and
  273 B). Same input to `encode_image_no_huffman` /
  `EncodeImageNoHuffman`, so this is a backward-refs / Huffman difference
  on the sub-image path. Small (≤0.05 %).
* **The main image is where the gap lives, and it is the histogram
  clustering, not the residuals**: weather m5 pixels 400 778 B vs
  396 664 B (+4 114 B), archives m5 626 303 vs 621 840 (+4 463 B). Same
  residuals (same transforms), same `histo_bits=5`, same cache bits —
  but libwebp keeps **more Huffman groups** (12 vs 10, 25 vs 17; at m4
  15 vs 14, 27 vs 21), pays ~1 KB more for tables and saves 4+ KB on
  pixel data.

## 3. Empty tile histograms: a real libwebp difference, measured neutral

`ZENWEBP_TRACE=1` on weather m5: 366 of the 1364 16px tiles have an
**empty** histogram (fully covered by LZ77 copies that started in an
earlier tile). libwebp's `HistogramCopyAndAnalyze` drops those before
clustering (`image_histo->size` excludes them, and `HistogramRemap` gives
an empty tile the previous tile's symbol "to help future LZ77"); zenwebp's
`ClusterState::from_tiles` kept every tile active, so the entropy-bin
ranges, the stochastic phase's iteration and sample counts and its
RNG-driven pair picks, and the greedy queue all saw a 27 %-empty
population. `meta_huffman.rs` now mirrors libwebp (`Histogram::is_empty`,
inactive from the start, previous-tile symbol on remap; the combine cost
factor keeps using the RAW tile count like `image_histo_raw_size`).

Measured: −210 B over the 22 cells (−0.001 %), zero change in any group
count, `dev/byteparity_sweep.rs` unchanged at 3080/3080 base + every
axis incl. alpha 192/192 byte-identical with libwebp. It is kept as a
parity correction (it is what libwebp does and it changes the entropy
image for the better on some files), not as a size win. `dev/output_hash.rs`
COMBINED moves `b1309ba43b9b5e43` → `5bd48ee3963f2783` (the lossless and
the lossy-alpha sections; the alpha plane is a VP8L image with empty
tiles too).

zenwebp's phase counters for weather m5 (both `build_meta_huffman` calls,
cache 0 and cache 10): 2728 tiles → entropy-bin merges 1775 → 218 active
→ stochastic 132 merges → 86 → greedy 60 merges → 26 final (13 per call
on average; the encoder shipped 10 groups). Whether libwebp's phases
stop earlier (fewer merges) or its remap keeps more groups referenced
cannot be told from zenwebp's side alone.

## 3b. Found: `HistogramCombineEntropyBin`'s `try_combine` gate was missing — −0.116 %

Reading `HistogramCombineEntropyBin` side by side with
`entropy_bin_combine_phase` for the pair-cost harness in §5 turned up the
divergence before the harness was needed. libwebp does **not** merge every
same-bin pair that passes the cost test: it first checks `try_combine` —
the combined histogram must keep trivial red/blue/alpha symbols, or both
candidates must already be non-trivial in one of those channels — and
otherwise counts a failure for the bin (up to 32 per bin, after which it
merges regardless). Merging a trivial-symbol tile into a non-trivial group
throws away that group's single-symbol codes, which is why libwebp keeps
more groups. zenwebp merged on the cost test alone. Ported
(`meta_huffman.rs`, `MAX_COMBINE_FAILURES = 32`, RED/BLUE/ALPHA =
`trivial_sym[1..=3]`).

## 3c. Found: two `HistogramCombineStochastic` details — another −0.023 %

Two more divergences in the stochastic phase, again by reading, both
ported in `stochastic_combine_phase`:

1. libwebp tightens the push threshold **inside** the sampling loop:
   `if (curr_cost < 0) { best_cost = curr_cost; ... }`, so after a better
   pair is found only pairs better than it are queued for the rest of the
   iteration. zenwebp kept `best_cost` fixed for the whole iteration and
   let worse pairs into the 9-slot queue, which persists across iterations.
2. `HistoQueuePush` orders a pair by compact position (`idx1 < idx2`) and
   the merge keeps `idx1`'s slot, removing `idx2` by swapping the last
   histogram into it. zenwebp merged into whichever index the RNG drew
   first, so its compaction — and every later RNG-driven pick — diverged.

## 4. What was checked and found equivalent

`VP8LGetHistoImageSymbols` vs `cluster_histograms`: entropy-combine
gating (`size > bins*2 && quality < 100`), `GetCombineCostFactor`
(raw size, quality 75 both sides — webpx's `new_lossless()` defaults to
75 like zenwebp), the stochastic `threshold_size = 1 + round(q³·99/10⁶)`
= 43, `HistogramCombineStochastic`'s outer loop (size-9 queue, Lehmer RNG,
`outer_iters = size`, `num_tries = size/2`, `tries_with_no_success`) —
its inner threshold update and pair ordering were NOT, see §3c —,
`HistogramCombineGreedy`'s loop shape (all pairs, pop intersecting, push
new pairs against the accumulator, merge while `cost_diff < 0`), and
`HistogramRemap` (per-tile best group by `HistogramAddThresh`).
`HistogramCombineEntropyBin` was NOT equivalent — see §3b.

## 5. Next chunk

The remaining candidate is the pair cost itself —
`GetCombinedHistogramEntropy` / `VP8LHistogramEstimateBits`
(`PopulationCost`, `VP8LBitEntropy`'s trivial-symbol and `is_used`
handling, extra-bits costs) vs `get_combined_histogram_cost_with_detail` —
because small numeric differences in the merge threshold shift merge
decisions across ~1000 tiles and fewer groups is exactly what a
systematically lower combined cost produces. libwebp-sys only exposes the
public encode API, so this needs a differential harness against
libwebp's *internal* cost function: a patched copy of `histogram_enc.c`
(the vendored source is at `~/.cache/cargo-read/libwebp-sys-0.14.4/vendor`
after `cargo read libwebp-sys`) that logs `(cost1, cost2, combo, diff)` per
`HistoQueuePush` and the per-phase group counts, built as a `dev/` C
harness, diffed against `HISTDBG` (`mode_debug`, already wired in
`HistoQueue::push`) on the same refs. The 2026-07-16 investigation
(52ef0e3) built exactly that instrumented tree and lost it with `/tmp`;
this time it goes in `dev/`.
